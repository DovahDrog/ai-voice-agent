# Security and privacy

## Intended use and trust boundary

This is a portfolio demonstration of a protected voice-tool backend, not a production-ready telephony deployment. A hosted orchestrator is a separate trust boundary. Model outputs, caller input, local audit files, provider responses and unsigned event callbacks are untrusted data. The public example contains only synthetic fixtures and reserved example domains.

No real credentials or account defaults are supplied. No live service is required to run the smoke/test suite. Do not publish runtime files, transcripts, audio, private `.env` values, provider configuration exports or credentials.

## Authentication

All `/tools/*` routes, including audit reads, depend on `X-Voice-Webhook-Secret`. The server requires a fresh `VOICE_TOOLS_SHARED_SECRET` between 32 and 512 characters:

- absent/short/oversized configuration → **503**;
- configured secret with missing/wrong header → **401**;
- correct secret → normal argument validation and tool processing.

Use a random value generated by `secrets.token_urlsafe(32)` or your approved secret-management system. Header values are compared as bytes with `hmac.compare_digest`. Neither the secret nor provider credentials are included in manifests/logs. There is no tenant/user authorization model or built-in secret rotation/replay protection. TLS termination and limited access are operator responsibilities.

## Delivery must be explicitly enabled

The default is local intent logging. Optional SMS/email submission requires **all** of the following:

1. `VOICE_DEMO_MODE=false` exactly; other values keep demo mode on.
2. The relevant `VOICE_SMS_DELIVERY_ENABLED` or `VOICE_EMAIL_DELIVERY_ENABLED` flag enabled.
3. The relevant provider set to `ghl` or `leadconnector`.
4. Fresh operator-supplied `VOICE_GHL_API_TOKEN`, `VOICE_GHL_LOCATION_ID`, `VOICE_GHL_API_BASE_URL` and `VOICE_GHL_ALLOWED_API_HOSTS`.
5. A confirmed recipient and nonempty `permission_evidence` plus strict boolean `permission_confirmed=true`.
6. Clean local suppression and URL checks; a provider contact whose channel recipient matches the request and whose known suppression flags do not block.

The account/API values are deliberately blank in `.env.example`; no production hostname, reusable password or fallback legacy credential is shipped. The backend does not auto-load `.env` files. Adapter helpers also check gates rather than relying only on routes.

Booking SMS and operator transfer remain placeholders even with these flags. Snapshot adapters may create an external CRM contact once explicitly enabled; close-packet SMS requires an existing matching contact. These are real potential side effects, not harmless provider tests. Enabling them requires separate authorization and provider-specific review.

## Consent and suppression limitations

Permission fields are **assertions from an authenticated orchestrator**, not independently checked recordings or legal authorization. A compromised/incorrect orchestrator can misstate consent. No blanket regulatory-compliance claim is made. The example prompt tells the assistant to collect channel-specific permission, honor opt-out and stop on failed suppression. A real consent ledger and jurisdiction/provider review are deployment prerequisites.

`do_not_call` on a known prospect records cross-channel suppression using normalized phone/email and known contact identifiers. Subsequent email can be blocked even without a phone. Unknown prospects return 404 instead of falsely claiming suppression. Invalid suppression JSON or semantically empty records block processing with 503. There is no automatic expiration/removal of suppressions.

Local suppression is not a provider-wide unsubscribe/STOP synchronization service. The event receiver does not process inbound STOP or unsubscribe messages; operators need a trusted, separately designed channel/event integration. Recognized provider DND flags are checked during contact verification, but this is not comprehensive provider-policy enforcement or cross-account contact discovery.

## URL and transport controls

Side-effect links require HTTPS and **exact**, explicitly allowed hosts. Reject IP literals (including alternate numeric/IPv6 forms), localhost/internal aliases, userinfo, nonstandard ports, raw controls/whitespace/backslashes and malformed hosts even when configured as allowed. Structured follow-up links and recognizable outgoing-text URLs share these controls. Subdomain/wildcard approval is not inherited.

Links are not fetched or DNS-resolved by validation. Approved-domain ownership, content, redirects and DNS are operator responsibilities; a valid URL is not proof of a trustworthy destination. Obfuscated/non-URL text can still mislead a recipient. Do not treat allowlisting as a general prompt-injection or phishing solution.

Optional provider transport rejects private/non-public DNS answers, connects to the resolved/checked address, retains standard certificate/hostname checks, disables environment proxies and blocks redirects so bearer tokens are not forwarded. Error bodies/exception details are not reflected to callers. Responses are size-bounded. DNS/redirect logic is exercised with local mocks; live provider/TLS behavior remains unverified.

## Minimized logging and private storage

The unsigned `/retell/webhook` accepts at most 64 KiB of JSON. Only timestamp, one of `call_started`/`call_ended`/`call_analyzed` (or `unknown`), byte count and `trusted=false` are logged. It is intentionally **not an authenticated provider event** and cannot authorize any action. Invalid/oversized bodies are rejected without raw-body logging.

Outbound intent/sent logs omit recipients, message bodies and consent quotations. Outcome notes and escalation reason/context are not persisted. Provider message identifiers may be retained in delivery metadata. Authenticated response previews and local audit data can contain caller content.

**Prospect and suppression records still contain caller-provided personal information.** The runtime directory must be private, access-controlled and excluded from backups/publication where inappropriate. The app does not provide encryption-at-rest, retention enforcement, a personal-data deletion interface or protection against a malicious local filesystem operator. It assumes its runtime directory is trusted and not attacker-writable/symlinked. `.gitignore` is a safeguard, not a data-security guarantee.

## Before any public deployment

Independent review must address TLS, request/rate limits, event signature and replay verification, consent/suppression synchronization, secret lifecycle, access control, retention, a transactional datastore, deduplication/idempotency, job reconciliation, monitoring and provider-specific testing. Tool bodies have field limits but need an upstream request-size limit too. Public metadata events can still be spoofed or used to exhaust storage without rate limiting.

There is no exactly-once guarantee: a provider may accept a message before a subsequent local write fails, and a caller retry could duplicate it. `sent=true` describes API acceptance, not inbox/handset delivery. No hosted speech session, real email/SMS, carrier behavior, live webhook signature, clean dependency installation or online vulnerability scan is claimed as validated.

Do not include secrets or caller data in public bug reports. This export contains no live deployment or private support contact; use only synthetic reproductions and the repository owner's chosen reporting channel.
